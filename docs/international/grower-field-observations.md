# Explicit field observations from dated grower tasks

Dated tasks previously offered a checklist tick and a planned-date calendar. Growers can now choose **Record what happened**, enter an observed calendar day and note, and explicitly confirm their observation. The date starts blank; the planned date is displayed separately and is never copied into the observation.

The action appends to the existing field journal, not a second activity ledger. It links the note to the original checked scope, persistent planting ID, bed and exact planned event. The entire current canonical book and its measured-source context must still resolve that membership. Proposal-local cycle ordinals, query parameters and displayed crop labels grant no link or access. Checklist, harvest, stock and sales records are unchanged. Planned interval ends and next-entry boundaries do not prove clearing, free land or another planting.

The journal retains the original link through ordinary edits and reloads. Its screen and selected CSV/HTML copies share a description that distinguishes the planned reference from the note's observed date. This saved reference is not rechecked against live plantings by the diary or export. Canonical planting and site IDs are excluded from the new summary; existing optional bed tags keep their previous export policy.

## Journal persistence

An older loaded app writes v1 and cannot preserve new link metadata. Personal journals now use one protected v2 canonical/evidence pair. Initial setup transports the exact old JSON-array bytes without interpreting or repairing its rows. The old copy remains evidence. A later v1 write leaves v2 intact and produces a visible conflict; the grower must download the copies and explicitly choose before any acknowledgement. Counts do not verify their contents. A real browser Web Lock permits one document to edit; other tabs can read the saved journal.

Guest transfer uses the existing serialized account/epoch boundary, preserves an existing destination and clears a source only after a confirmed destination pair. Crop migration and personal-profile defaults remain separate. Sample observations remain in the established temporary v1 sample shim and do not write personal canonical keys.

Ordinary edits require the original loaded list's private actor/sample epoch and exact raw receipt. New task notes additionally recheck current planning sources after asynchronous work. Duplicate JSON members, numeric overflow or precision loss, hidden/malformed rows, changed references and unsafe runtime descriptors cannot become permission to replace old evidence. Unknown JSON metadata is retained. Candidate edits cannot retag a linked note into another bed. The final specific write receipt and intended bytes must match; an uncertain performed write is held and is never described as a failed save inviting repetition. Capacity or model holds preserve the draft and saved data; they are not an automatic repair service.
